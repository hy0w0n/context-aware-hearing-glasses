# 오디오 전처리·전송 조건이 소리 분류 모델 입출력에 미치는 영향 — 오프라인 재현 실험

작성 2026-10-03 · 재현 스크립트 `tools/audio_pipeline_eval.py` (약 70~80초, 결정적 — 시드 고정)
**성격: PC 오프라인 시뮬레이션.** 실제 모델(`android/app/src/main/assets/soundModel.tflite`)과 앱과 동일한 전처리 코드를 사용했지만, BLE 링크 위에서 실측한 값은 아니다(실측 손실률은 README 「4. 측정 결과」의 블루투스 오디오 전송 참조).

## 1. 질문

빔포밍된 16kHz 오디오가 안경 → 앱으로 전달되어 소리 분류 모델에 들어갈 때, 다음 세 조건이 **모델 입력(MFE 특징)과 출력(클래스 확률·판정)**에 얼마나 영향을 주는가.

1. 입력 정규화 — 앱의 전처리가 학습 전처리(클립별 피크 정규화)와 다르면 어떻게 되는가
2. ADPCM 4:1 압축 — 전송량을 1/4로 줄이는 손실 압축이 분류 결과를 바꾸는가
3. BLE 패킷 유실 — 패킷이 통째로 사라졌을 때 앱이 버퍼를 채우는 방식(이어붙임)이 결과에 어떤 영향을 주는가

## 2. 방법

### 2.1 모델과 전처리 (앱과 동일)
| 항목 | 값 | 근거 |
|---|---|---|
| 모델 | Edge Impulse MFE+CNN, INT8, 클래스 `[danger, noise, speech]` | `sound_model/`, `SoundClassifier.kt` |
| 입력 창 | 16kHz mono 2.0초 = 32,000샘플, 창 이동 1초 | `SoundClassifier.WINDOW`, `sound_eval.windows` |
| 올바른 전처리 (a) | 창 피크 → 32767 정규화 → 프리엠퍼시스 y[n]=x[n]−0.98·x[n−1] → ÷32768 → MFE(프레임 320/스트라이드 160, FFT 256, 멜 32, noise floor −52dB, 1/256 반올림, [0,1] 클립) | 2026-10-03 수정된 `SoundClassifier.classifyBuffer()`, `tools/sound_eval.py` |
| 판정 규칙 | argmax 확률 ≥ 0.6이면 그 클래스, 아니면 noise | EI 기본 임계 |
| 무음 게이트 | 원값 RMS < 150이면 모델을 돌리지 않음 | `SILENCE_RMS` |

전처리·MFE·양자화는 `tools/sound_eval.py`를 import 해서 그대로 썼다(이 파일은 앱 Kotlin 코드와 대응되는 Python 포팅).

### 2.2 패킷 단위
펌웨어 `config.h`의 `DSP_OUT_SAMPLES = BLE_AUDIO_SAMPLES = 240` → **AUDIO 패킷 1개 = 240샘플(15ms)**, BLE notify 1개 = 패킷 1개. PCM16·ADPCM 모두 같은 샘플 수(ADPCM은 니블 120바이트 + 상태 3바이트). 본 실험의 패킷도 240샘플.

### 2.3 ADPCM
펌웨어 `firmware/src/adpcm.cpp`의 IMA ADPCM 인코더를 Python으로 한 줄씩 포팅(스크립트 내 `AdpcmEncoder`), 디코더는 PC 수신기가 쓰는 `tools/ima_adpcm.py`. 펌웨어와 같이 패킷마다 "인코딩 직전 상태(predictor, step_idx)"를 헤더에 싣고 수신측은 패킷마다 그 상태로 디코드(패킷 단위 리싱크). 검증: 헤더 리싱크 디코드 == 연속 디코드(샘플 단위 일치), 1kHz 사인(진폭 10000) 왕복 SNR 27.7dB(구현 당시 기록 26.8dB와 같은 수준).

### 2.4 패킷 유실 모델 — 앱이 실제로 하는 방식
`BleLink.kt`/`WifiLink.kt`는 seq 공백을 `drops` 카운터에 더하기만 하고, `MainActivity.onAudio → SoundClassifier.push()`는 **받은 프레임을 링버퍼에 순서대로 넣는다. seq로 빈 자리를 0으로 채우는 코드는 없다.** 따라서 유실이 생기면 2초 창 안의 오디오는 **시간 압축**된다(유실 비율만큼 더 과거 오디오가 창에 끌려 들어오고, 유실 경계마다 파형 불연속이 생김). 이 방식을 **"이어붙임(앱 모델)"**이라 하고, 비교용으로 유실 자리를 0으로 채워 시간축을 보존하는 **"0채움(앱 미구현)"** 변형도 같이 돌렸다.

- 유실: 패킷마다 독립(iid) 확률 p로 통째 유실, p ∈ {0, 3, 10, 28}% (28.4/31.6% = 간섭 링크 PCM 실측, 2.9~3.3% = 간섭 링크 ADPCM 동시 전송 실측), 시드 20개
- 평가 창: 원래 시간축에서 3.0초부터 약 1.0초(67패킷) 간격, 각 시각에 "그때까지 수신된 마지막 32,000샘플"(= 앱 링버퍼 내용). 기준 = 유실 0%의 같은 시각 창
- 2초짜리 클립(test_sound.pcm)은 유실 뒤 2초를 채울 과거 샘플이 없어, 실제 저레벨 스트림 녹음(wav260910041425) 첫 2초를 앞에 붙인 4초 스트림의 마지막 창 1개를 평가(유실 0%면 창 = 클립 자체). 참고: 클립 자체를 2회 반복한 스트림으로도 같은 경향(10%에서 최저)이 나왔다
- ADPCM+유실은 별도 셀로 두지 않았다. 헤더 리싱크 덕에 "디코드 후 유실"과 "유실 후 디코드"가 샘플 단위로 같기 때문에 실험 2와 3의 결과를 합성하면 된다

(28%에서 긴 클립 두 개는 각각 1개(시드×창)가 "첫 평가 시각까지 수신 샘플 32,000개 미달"로 이어붙임 평균에서 빠졌다. 0채움에는 해당 없음.)

**읽는 법**
- 앱이 실제로 하는 **이어붙임** 방식에서는 3% 유실(ADPCM 간섭 링크 수준)만으로도 판정 일치율이 76~95%로 떨어지고, 28%(PCM 간섭 링크 수준)에서는 **57~67%**(danger 클립은 95%)까지 내려간다. 3% 유실은 2초 창에 평균 4개의 불연속 경계를 만든다.
- 같은 유실률이라도 **0채움**이 거의 모든 셀에서 더 안정적(3%: 85~100%, 10%: 70~100%). 특히 danger 클립은 10%까지 100% 일치. 유실이 생겼을 때 시간축을 보존하는 쪽이 모델에 덜 해롭다는 뜻이며, 앱에 seq 기반 0채움(또는 직전 패킷 반복)을 넣을 근거가 된다.
- danger 클립의 이어붙임 결과는 **비단조**(3% 0.86 → 10% 0.63 → 28% 0.91). 5~20%를 추가로 돌려본 결과 5~10%에서 noise로 뒤집히는 시드가 가장 많고(20개 중 8~9개) 20% 이상에서는 다시 danger로 돌아왔다. 앞에 붙인 오디오를 바꿔도(클립 자체 반복) 같은 경향이라 접합 내용물보다 **불연속 경계의 개수·간격이 MFE 프레임 격자와 상호작용하는 것**이 원인으로 보이나, 확정은 못 했다. 평균만 보면 28%가 괜찮아 보이지만 표준편차(0.097)와 10%의 붕괴를 함께 봐야 한다.
- 손실률 수치(3·10·28%)는 2026-09-10 PC 동글 실측값을 빌린 것이고, 여기서 유실은 iid로 뿌렸다. 실제 BLE 유실은 이미지 전송 버스트에 몰려서(군집) 발생하므로 같은 손실률에서도 창 내 영향은 다를 수 있다.

## 4. 종합 해석

1. **정규화가 가장 큰 변수다.** 구 버그(원값 직접)는 입력과 무관한 고정 출력(danger 0.73)이었고, 피크 정규화를 빼면 레벨이 클래스를 결정한다. 올바른 파이프라인은 −30dB까지 출력이 거의 불변이다(무음 게이트 범위 내).
2. **ADPCM 4:1은 분류에 거의 영향이 없다.** 41창 중 40창 판정 일치, 확률 변화 대부분 ≤0.01. 전송량 1/4로 간섭 링크 손실 28%→3%(실측)를 사는 대가로는 작다. 단 충격음에서는 SNR이 20dB 아래로 떨어지고 임계 근처 창은 뒤집힐 수 있다.
3. **패킷 유실은 압축보다 분류에 훨씬 해롭다**, 그리고 그 해로움의 상당 부분은 앱이 유실을 "이어붙여" 시간을 압축하는 방식에서 온다. 같은 유실률에서 0채움이 더 안정적이므로, 다음 앱 수정 후보는 seq 기반 0채움(또는 패킷 반복)이다.
4. 따라서 "속도/대역 개선(ADPCM) → 유실 감소 → 모델 입력 보존"의 연결이 데이터로 성립한다: 압축 자체의 분류 영향(≤0.01)은 유실 3%의 영향(|Δp| 0.06~0.09)보다 작다.

## 5. 한계 (슬라이드·설명서에 쓸 때 반드시 함께 적을 것)

- **전부 PC 오프라인 시뮬레이션.** 실제 BLE 위에서 모델 출력을 기록한 것이 아니다. 손실률 수치는 2026-09-10 PC 동글(bleak) 실측에서 빌렸고, 폰 실기기 손실률은 측정하지 않았다.
- 유실을 iid 확률로 뿌렸다. 실제 유실은 이미지 버스트에 군집한다.
- 테스트 클립 6개 중 라벨이 분명한 것은 3개(test_sound=danger 기대, 핑거스냅, 합성 백색소음)이고 나머지는 내용 미라벨이라 정답률이 아니라 "출력 안정성"만 계산했다. 창 수도 적다(1~19창).
- 핑거스냅 클립은 48kHz raw ch1을 PC에서 변환한 **파생** 신호(빔포밍 미적용). 펌웨어 빔 출력과 레벨·스펙트럼이 다를 수 있다.
- blewav 클립은 이미 ADPCM을 거쳤을 가능성이 있어 실험 2의 해당 행은 2회 압축에 해당한다.
- −20/−30dB 조건은 앱 무음 게이트를 무시하고 모델을 돌린 값이다. 앱에서는 그 창의 대부분이 '무음'으로 처리된다.
- 모델 정확도(88.3% 등)는 호연 보고서의 수치이며 이 실험에서 재측정하지 않았다.
